 # SpeedyCRM — Архитектурная Multi-Bot SaaS Платформа 🥊🚀

Высокопроизводительная CRM-система для автоматизации спортивных клубов, студий и франшиз, построенная по модели SaaS (Software as a Service).

Проект полностью развернут в Production-режиме, работает на **вебхуках (Webhooks)** и изолирован внутри контейнеров Docker на сервере Aezza под управлением Nginx с автоматическим Wildcard SSL-шифрованием.

---

## 🔥 Что было реализовано в рамках технического рефакторинга:

### 1. Переход на монолитную архитектуру Webhooks (FastAPI + Aiogram 3)
* **Реактивный отклик:** Полностью ликвидирован опрос сервера (`polling`). Бот переведен на вебхуки. Telegram доставляет апдейты мгновенно через POST-запросы.
* **Слияние процессов:** Код Telegram-ботов и веб-страниц FastAPI объединен в единое сердце внутри одного Docker-контейнера `gym-api`. Управление сессиями и ботами встроено в современный жизненный цикл приложения (`lifespan`), что сэкономило оперативную память сервера.
* **Multi-Bot Dynamic Routing:** Платформа поддерживает одновременную работу бесконечного количества ботов. При старте система вытягивает активные токены из PostgreSQL, инициализирует их и генерирует для каждого уникальный защищенный URL-адрес вебхука вида `/webhook/bot/{token}`.

### 2. Инфраструктура Nginx & Wildcard SSL (Let's Encrypt / Certbot)
* **Динамические SaaS-поддомены:** Реализована классическая архитектура SaaS. Nginx и FastAPI перехватывают заголовок `Host`, парсят адрес и вытаскивают поддомен (например, `https://speedycrm.ru`). Бэкенд на лету понимает, данные какого именно клуба (`club_id = 123`) нужно отобразить.
* **Wildcard SSL:** Через Docker-контейнер Certbot выпущен единый сертификат Let's Encrypt со звёздочкой (`*.speedycrm.ru`), защищающий основной домен и абсолютно все ID-поддомены клиентов по протоколу HTTPS (порт 443).
* **Авто-редирект:** Все входящие незащищенные запросы с 80 порта (HTTP) принудительно перенаправляются на защищенный 443 порт (HTTPS).

### 3. Умная инлайновая авторизация и Слияние Аккаунтов
* **Сквозной Сценарий (User Flow):** Решена проблема рассинхронизации. Когда администратор на ресепшене вручную вносит атлета в базу и указывает телефон родителя, запись создается с `parent_id = None`.
* **Авто-вход:** При первом старте бота система проверяет Telegram ID, уходит в ветку отсутствия авторизации и выводит кастомную кнопку `request_contact=True`.
* **Слияние «на лету»:** Как только родитель нажимает *«📱 Войти по номеру телефона»*, бот очищает номер до 10 цифр, находит по индексу в PostgreSQL запись админа и жестко прописывает туда Telegram ID пользователя, открывая личный кабинет без повторного ввода данных.

### 4. Изоляция путей и SqlAdmin (Суперадминка)
* **Разделение прав:** Чтобы исключить конфликт роутов в FastAPI, веб-интерфейс администратора для Telegram WebApp освободил путь `/admin`.
* **Суперадмин-панель:** Полноценный интерфейс управления всей СУБД для главного разработчика (`sqladmin`) перенесен на секретный защищенный путь `/master-dashboard`, позволяя управлять франшизами и подписками в один клик. Кнопка быстрого перехода в SqlAdmin встроена прямо в закрытую клавиатуру суперадмина в Telegram.

### 5. Автоматизация SaaS-задач (APScheduler)
В фоне развернут асинхронный планировщик задач, который без участия разработчика выполняет критически важные бизнес-процессы:
* **Контроль прогульщиков (10 дней):** Ровно в 10:00 система сканирует поле `last_visit` и отправляет триггерные уведомления родителям, чьи дети пропустили 10 дней занятий при активном балансе абонемента.
* **Поздравление с Днем Рождения:** Автоматический утренний парсинг колонки дня рождения атлета (накатанной через миграции Alembic) с отправкой праздничных открыток.
* **Авто-бэкапы СУБД:** В 23:00 система делает полный слепок PostgreSQL, генерирует файл Excel через Pandas, отправляет его суперадмину в личку в Telegram через `BufferedInputFile` / `FSInputFile` и бесследно удаляет временный файл с диска сервера, соблюдая чистоту хранилища.
* **Вечерние бизнес-отчеты:** В 22:00 владельцы всех клубов (`owner_id`) получают персональную сводку по выручке, количеству отмеченных посещений за день и активным абонементам.

### 6. DevOps и CI/CD
* Проект полностью упакован в **Docker Compose** (PostgreSQL 15, Redis 7, Nginx Alpine, FastAPI, Certbot).
* Настроен `.dockerignore`, исключающий мусорные файлы и кэш из сборки образов.
* Развернут автоматический пайплайн **GitHub Actions** (воркфлоу тестов и проверок синтаксиса, собирающийся без ошибок при каждом пуше в ветку `master`).

## 🔒 Модуль биометрического прохода (Telegram WebApp СКУД)

Инновационная система авторизации и контроля доступа (СКУД) в спортивные клубы с использованием нативных технологий аппаратной биометрии смартфона (**FaceID / TouchID**) через Telegram WebApp. Модуль полностью заменяет уязвимые QR-коды (которые можно скомпрометировать или переслать скриншотом) на сквозную цифровую подпись, жестко привязанную к криптографическому ключу устройства родителя.

### 🚀 Архитектура и сквозная цепочка взаимодействия

1. **Telegram-Бот (Точка входа):**
   Родитель переходит в свой профиль. Бот с помощью `SimpleNamespace` собирает контекст и генерирует инлайн-клавиатуру с изолированной ссылкой на WebApp под конкретный SaaS-поддомен клуба: `https://{club_id}.speedycrm.ru/webapp/biometric-pass?club_id={club_id}&user_id={user_id}`.
2. **Фронтенд (Telegram WebApp JS API):**
   * **Первый заход (Активация устройства):** Скрипт через `Telegram.WebApp.BiometricManager` проверяет поддержку биометрии. Если доступ не настроен (`bm.isAccessGranted = false`), список детей блокируется, и вызывается аппаратный метод `bm.requestAccess()`. iOS/Android генерирует пару ключей безопасности, а фронтенд отправляет POST-запрос на `/webapp/enable-biometry`, фиксируя в БД `is_biometric_enabled = True`.
   * **Вызов FaceID из нативного контекста:** В целях безопасности Telegram блокирует запуск биометрии из обычных HTML-тегов (`onclick`). Интерфейс переведён на использование **`tg.MainButton`**. При клике на карточку атлета (например, Адама Омарова) в интерфейс мессенджера выезжает нативная кнопка Telegram, нажатие на которую легитимно вызывает метод `bm.authenticate()`. Мессенджер генерирует уникальный `biometric_token`.
3. **Бэкенд (FastAPI Security & Бизнес-логика):**
   * **Криптографическая валидация:** Метод `verify_telegram_data` парсит `init_data` и вычисляет хэш через HMAC-SHA256 с использованием секретного `bot_token` конкретного клуба. Это полностью исключает подмену `user_id` злоумышленниками через прямые HTTP-запросы.
   * **Скоринг абонемента:** Бэкенд проверяет статус студента: отсутствие заморозки (`is_frozen`), валидность даты окончания (`expire_date`) и наличие доступных тренировок (`balance_lessons > 0`).
4. **Контроллер железа (Интеграция с IoT):**
   FastAPI извлекает конфигурацию СКУД из JSONB-поля настроек клуба (`club_settings`) по системному ключу **`"turnstile"`**.
   * **Адаптивный парсинг:** Объект SQLAlchemy принудительно приводится к чистому словарю Python (`dict()`), а встроенный предохранитель проверяет KeenDNS-адрес (если буквенный домен записан без протокола, на лету наклеивается `http://`).
   * Асинхронный модуль `skud.py` отправляет CGI-команду (`relay_cgi.cgi`) на удалённую релейную плату **Dingtian** в клубе. При ответе `200 OK` транзакция закрывается: у студента списывается занятие (`balance_lessons -= 1`), обновляется `last_visit`, база делает `db.commit()`, а WebApp обновляет баланс на экране.

## 🛠 Выполненный рефакторинг и оптимизация системы (07.07.2026)

За прошедший спринт была проведена масштабная оптимизация бэкенда (Aiogram 3 + FastAPI) и развернута отказоустойчивая система потокового видеонаблюдения для SaaS CRM.

### 1. Монолитизация и ускорение админ-панели (Устранение зависаний)
* **Асинхронные цепочки FSM**: Исправлен критический deadlock асинхронного движка `aiogram 3.x`, из-за которого бот намертво зависал при удалении расписания (`query is too old`). Хендлеры отрисовки дней переведены на универсальный фильтр `StateFilter("*")` [INDEX], что полностью изолировало контекст навигации.
* **Защита инстансов Pydantic v2**: Устранена ошибка валидации (`Instance is frozen`) при попытке мутации защищенного объекта `CallbackQuery.data` [INDEX]. Логика возврата на шаги переписана на безопасную передачу параметров через чистые аргументы функций (`manual_day`).
* **Отказоустойчивость SaaS-оферты**: Опасный метод `.scalar_one_or_none()` в ORM SQLAlchemy заменен на безопасный `.scalars().all()`. Система принятия юридических правил теперь полностью защищена от падения (ошибки `MultipleResultsFound`), если у одного родителя в клубе привязано несколько профилей атлетов.
* **Принудительное обновление кэша профилей**: В хендлер личного кабинета внедрен флаг `.execution_options(populate_existing=True)`. Это заставило SQLAlchemy игнорировать внутренний Identity Map кэш и отдавать пользователю моментально измененный баланс занятий прямо из PostgreSQL.

### 2. Интеграция LIVE-видеонаблюдения через Серый IP и 4G-модем (KeenDNS + Docker)
* **Проблема**: Камера Tiandy (кодек H.265) установлена в зале за 4G-роутером Keenetic с серым IP-адресом. Облачный режим KeenDNS (веб-ретранслятор) жестко блокирует «чистые» бинарные RTSP-потоки и Basic-авторизацию, из-за чего в Telegram WebApp отображался черный/серый экран.
* **Решение**:
  1. В админке камеры авторизация переведена на криптографический режим `digest/basic` для легального прохождения внешних запросов.
  2. На удаленном VPS-сервере в единую Docker-сеть (`web_network`) рядом с ботом развернут медиасервер **`go2rtc`** [INDEX].
  3. Написан прокси-роут на FastAPI (`StreamingResponse`), который по внутренней сети Docker асинхронно забирает поток у `go2rtc` через HTTP-туннель KeenDNS [INDEX], на лету адаптирует H.265 видео в понятный для мобильных устройств формат и транслирует байты в WebApp.
  4. Для обхода жесткого кэширования встроенного браузера Telegram в инлайн-кнопку WebApp внедрен динамический cache-buster на базе timestamp (`&v={time}`), а запросы плеера перенаправлены на основной защищенный HTTPS-домен для обхода CORS-блокировок [INDEX].

### 💳 Модуль интернет-эквайринга Т-Банка (Т-Касса) с оплатой в 1 клик

Реализована официальная белая онлайн-оплата абонементов по картам, работающая параллельно со старой схемой ручных переводов по СБП. Система позволяет сохранять токены карт пользователей для проведения быстрых последующих платежей.

#### 🛠 Что конкретно сделано:
* **База данных (PostgreSQL + SQLAlchemy)**: Созданы таблицы `subscriptions` (для хранения токенов привязанных карт) и `payment_orders` (для логов транзакций). Накачена миграция Alembic на сервере.
* **Сервис API-клиента (`services/tbank_client.py`)**: Написан асинхронный клиент на `httpx` для взаимодействия с API Т-Банка с автоматической криптографической генерацией подписей запросов (`Token` SHA-256).
* **Конфигурация (`config.py` & `.env`)**: Все доступы к кассе (`TerminalKey`, `SecretKey`, вебхук URL) полностью изолированы от кода, вынесены в центральный конфиг и безопасно считываются из переменных окружения докера.
* **Разводящее меню в боте (`handlers/payments.py`)**: Хендлер `set_tariff_` переписан в умную развилку. Если у родителя в БД нет привязанной карты, бот предлагает выбор между СБП (ручной чек) и онлайн-оплатой. Если карта уже привязана — выводится кнопка оплаты в 1 клик (`pay_one_click`), которая мгновенно проводит скрытый платеж `/Charge` без повторного ввода реквизитов.
* **FastAPI Обработчик (`admin_module/api.py`)**: Развернут POST-эндпоинт `/v1/payments/tbank/webhook` с валидацией подписи банка. При первой успешной оплате он вытаскивает `RebillId` карты и привязывает её к родителю, после чего автоматически вызывает родную функцию `add_abon()`, мгновенно начисляя уроки ребенку и отправляя родителю SaaS-уведомление через нужный бот из глобального `bots_dict`.

#### 🎯 Для чего это нужно:
Для превращения CRM в полноценную SaaS-платформу. Это избавляет админов клубов от ручной проверки сотен скриншотов чеков, автоматизирует финансовые потоки, а для клиентов (родителей) создает бесшовный опыт оплаты абонементов в одно нажатие прямо внутри интерфейса Telegram-бота.

## ⚙️ Управление миграциями и базой данных в Docker (SaaS)

В системе реализован автоматический накат миграций при каждом деплое через GitHub Actions. Однако при добавлении новых полей в модели (например, поля `discipline` в таблицу `students`), генерацию файлов миграций необходимо выполнять внутри изолированного Docker-контейнера.

### 🛠 Пошаговый чек-лист добавления полей в БД:

1. **Изменение модели в коде**:
   Добавьте необходимое поле в модель (например, в `models.py` или `db.py` для `Student`):
   ```python
   discipline: Mapped[Optional[str]] = mapped_column(String(50), nullable=True, default="boxing")
   ```

2. **Генерация файла миграции внутри контейнера**:
   Выполните команду на сервере, чтобы Alembic сравнил модели и создал файл в изолированной файловой системе:
   ```bash
   docker exec -it gym_crm_api alembic revision --autogenerate -m "add_discipline_to_student"
   ```

3. **Применение изменений к базе данных Postgres**:
   Накатите миграцию, чтобы поле физически появилось в СУБД:
   ```bash
   docker exec -it gym_crm_api alembic upgrade head
   ```

4. **Важно (Синхронизация с Git)**:
   Так как контейнер `gym_crm_api` перезатирается при следующем CI/CD деплое, сгенерированный на сервере файл миграции из папки `/app/migrations/versions/` сотрется.
   * **Решение**: Не забудьте продублировать добавление поля в код у себя на ПК в PyCharm, закоммитить и запушить изменения в репозиторий. Накат миграции на проде произойдет автоматически при старте.

## 🔄 Перезапуск всей инфраструктуры проекта

Если бэкенд FastAPI или прокси-сервер видеострима `go2rtc` зависли, либо нужно принудительно очистить логи и перезапустить фоновые SaaS-задачи (планировщики отчетов, рассылки), выполните полный рестарт контейнеров из корневой папки проекта:

```bash
docker compose down && docker compose up -d
```

* **`down`** — безопасно останавливает и удаляет контейнеры, сохраняя все данные в Postgres-volumes.
* **`up -d`** — поднимает инфраструктуру в фоновом режиме, инициализирует вебхуки Telegram-ботов и применяет актуальный `alembic upgrade`.
