# SpeedyCRM

## Продажа абонемента при создании атлета

Если при создании атлета выбран тариф, система создаёт подтверждённую наличную продажу в `payment_orders`, привязанную к этому атлету. Поэтому абонемент отображается в кассе, журнале операций и статистике продаж. Вариант «Без абонемента» платёжную запись не создаёт.

Поведение покрыто контрактными тестами:

```powershell
py -m pytest -q tests/test_student_subscription_sale_contract.py
```

> Рабочая документация проекта и эксплуатационный runbook. Боевые секреты,
> боевые сертификаты и production `.env` никогда не копируются в Desktop или Git.

## Production readiness и границы аудита

Перед релизом обязательны все проверки из этого раздела. Успешные реальные
платежи подтверждают работу платежного контура, но не заменяют проверку
миграций, резервного копирования, TLS, rollback и smoke-check.

Последняя локальная проверка должна включать:

```powershell
docker compose config --quiet
docker compose ps
docker compose logs --tail=100 gym-api nginx db
python -m pytest -q
python scripts/smoke_check.py
docker compose exec -T gym-api alembic current
docker compose exec -T gym-api alembic heads
```

Релиз запрещён, если API или Nginx имеют `Restarting`, миграции падают,
`/ready` не возвращает 200, smoke-check не проходит или нет проверенного
восстановления резервной копии.

## Локальный Desktop: запуск с нуля

Docker Desktop должен использовать Linux engine, BuildKit и не менее 6–8 ГБ
памяти. Адреса и порты не меняются:

```powershell
docker compose build gym-api
docker compose up -d
docker compose ps
python scripts/smoke_check.py
```

Локальная база хранится в Docker volume `pg_data`. Не выполнять `docker
compose down -v`, если нужно сохранить данные. Для локального HTTPS допускается
self-signed сертификат в `certbot/conf`; он не является production-сертификатом,
не должен коммититься и вызывает предупреждение браузера.

## Alembic: безопасный порядок работы

1. Перед изменением схемы сделать backup production и проверить restore на
   отдельной тестовой базе.
2. Создать новую миграцию из текущей головы:

   ```powershell
   docker compose exec -T gym-api alembic current
   docker compose exec -T gym-api alembic heads
   docker compose exec -T gym-api alembic revision -m "describe change"
   ```

3. Вручную проверить `upgrade()` и `downgrade()`: foreign key, индексы,
   unique/idempotency-ограничения, nullable и обратную совместимость.
4. Не редактировать опубликованные миграции и не менять их `revision` или
   `down_revision`: для исправления создаётся новая идемпотентная миграция.
5. Проверить чистую тестовую базу: `alembic upgrade heads`, затем запустить
   приложение и smoke-check.
6. На production миграции запускаются до старта приложения в том же release
   процессе. Не выполнять ручные `ALTER TABLE` вместо миграции.

Текущая compatibility-миграция `c3d9e7a1b2f4` идемпотентно создаёт таблицы,
которые отсутствовали в старом baseline (`subscriptions`, `payment_orders`,
`visit_logs`), и добавляет `provider_payment_id` только если его нет. На уже
существующей базе она не удаляет данные и не меняет существующие таблицы без
необходимости.

## Сертификаты и Nginx

Production сертификаты получает и продлевает Certbot на сервере. Локально
сертификаты не скачиваются с сервера: создаётся отдельный self-signed ключ в
`certbot/conf/live/speedycrm.ru/`, после чего выполняется:

```powershell
docker compose restart nginx
docker compose ps
docker compose logs --tail=50 nginx
```

Проверить наличие файлов можно без вывода ключа:

```powershell
Test-Path certbot/conf/live/speedycrm.ru/fullchain.pem
Test-Path certbot/conf/live/speedycrm.ru/privkey.pem
```

Боевой `privkey.pem` не передавать через чат, Git, Desktop или архив проекта.
После deploy проверить срок сертификата, цепочку, redirect HTTP→HTTPS и
доступность всех webhook URL.

## Release / rollback runbook

До deploy: сохранить commit, backup БД, список текущих контейнеров, текущую
версию Alembic и результат smoke-check. После deploy: проверить `ps`, логи,
`/health`, `/ready`, Telegram webhook, callback/webhook ЮKassa, повторную
доставку webhook и отсутствие двойного начисления.

Если миграция или приложение не стартовали: не удалять volume и не запускать
`down -v`; остановить только новый релиз, восстановить предыдущий image и
следовать проверенному rollback-плану. Для destructive-миграций нужен отдельный
двухфазный план expand → backfill → contract.

## Возможности

- личный кабинет родителя и несколько атлетов в одном клубе;
- регистрация и авторизация пользователей;
- абонементы, занятия, безлимитные тарифы и заморозка;
- QR-пропуска и проход через FaceID/WebApp;
- интеграция с турникетом СКУД;
- история посещений и статистика клуба;
- онлайн-оплата через ЮKassa, ручная оплата по чеку и заявка по реквизитам с подтверждением администратором;
- возрастной фильтр тарифа проверяется на стороне бота и в WebApp, включая корзину;
- сохранение карты для оплаты в один клик;
- авторизация WebApp через подписанные Telegram `initData`;
- админ-панель, суперадмин и рассылки;
- камеры через go2rtc;
- фоновые задачи APScheduler;
- настраиваемый загрузочный экран WebApp с логотипом клуба;
- премиальный чёрно-белый WebApp-кабинет клиента в стиле Checkmat Jiu-Jitsu;
- отдельный staff-pass WebApp для сотрудников: без QR, только быстрый проход турникета и аудит;
- WebApp-покупка абонемента, покупка заморозки, привязка профиля по номеру, история оплат и карточка атлета;
- в продаже товаров бариста может выбрать атлета, чтобы чек ушёл его родителю;
- Docker Compose, Nginx, CI/CD и автоматические тесты.
- реестр клубных ботов подхватывает новые токены без перезапуска Docker;
- отдельный audit-слой для ключевых SaaS-событий;
- роли сотрудников клуба с разграничением доступа: cashier / coach / manager / owner / super admin;
- короткий Redis-lock на открытие турникета, чтобы не дёргать реле дважды при одновременном проходе;
- отдельная WebApp-страница аудита клуба и кнопка аудита в панелях админа и супера;
- большой алерт бариста по товарным заказам, при этом полный чек остаётся у владельца;
- фильтр магазина по категориям работает на уже существующих товарах без изменения базы;
- нижняя панель быстрых действий в кабинете клиента сворачивается и разворачивается;
- `reload_cache` только добавляет недостающие значения и не затирает ручные настройки клуба;
- в админской панели СКУД и в общей админ-клавиатуре есть one-tap вход в турникет для owner/staff;

Production-контейнер запускается от непривилегированного пользователя `appuser`. Исходный код не монтируется поверх образа; отдельно сохраняются только логи и загруженные логотипы.

## QR, СКУД и посещения

### Постоянный сканер на планшете

Администратор открывает кнопку «ОТКРЫТЬ СКАНЕР (ВХОД)» один раз. Сканер размещён внутри CRM по адресу `/webapp/scanner?club_id={club_id}` и работает в постоянном режиме: после успешного прохода WebApp не закрывается, камера продолжает принимать следующие QR-коды. Завершение выполняется отдельной кнопкой на планшете.

QR передаётся напрямую в `POST /webapp/scanner/scan`, а не через Telegram `sendData`, поскольку `sendData` автоматически закрывает Telegram WebApp. Endpoint проверяет Telegram `init_data`, принадлежность администратора клубу, срок QR и HMAC-подпись, после чего использует общую логику СКУД. Уведомления о проходе отправляются администратору и родителю атлета.

После изменения сканера нужно увеличить версию URL (`v=...`) либо очистить кеш WebView на планшете.

### Расписание

Клиентское расписание доступно публично по `/webapp/schedule?club_id=...` и работает в режиме просмотра — это можно использовать как рекламную страницу клуба. Админское расписание открывается отдельно по `/webapp/admin-schedule`; доступ защищён Telegram `init_data` и ролью владельца/суперадмина. В админском WebApp можно добавлять, редактировать и удалять занятия по дисциплине и дню. Там же есть два вида копирования:

- копирование занятий внутри дня — переносит занятия из одного дня в другой в рамках одной дисциплины;
- копирование расписания между дисциплинами — переносит все занятия по дням из одной дисциплины в другую, например из «Джиу-джитсу» в «Грэпплинг».

Бот продолжает поддерживать прежнее управление расписанием.

### Аудит и роли

- `/webapp/admin-audit` — журнал действий клуба с фильтрами по роли, событию и датам.
- В админской и супер-панели есть кнопка `📜 Аудит`.
- В аудит пишутся действия по товарам, кассе, тарифам, расписанию, персоналу, ручным чекинам и настройкам.
- Для товарных продаж бариста получает отдельный большой алерт, а владелец — полный чек.
- Если при товарной продаже бариста выбрал атлета, сервер дополнительно отправляет чек родителю выбранного атлета.
- Для owner и активных staff есть отдельный staff-pass: без QR, без student-session, только быстрый проход и аудит.
- Существующие товары и категории не переписываются: фильтр магазина работает на нормализованной категории поверх текущих данных.

### План общей корзины

Следующий коммерческий модуль — единая корзина клуба. В неё можно будет положить абонемент, заморозку, мерч и напитки из кофейни и провести одной оплатой. Текущие отдельные сценарии оплаты не меняются: корзина должна работать поверх них через отдельный заказ с позициями, идемпотентностью и единым webhook. Для каждого товара сохраняются тип, цена, количество, клуб и параметры исполнения; после успешной оплаты позиции обрабатываются своими обработчиками.

Старый API-маршрут ручного открытия турникета `/open-turnstile` защищён заголовком `X-API-Key`. Пользователи его не вводят: пользовательский WebApp использует отдельный маршрут `/webapp/open-turnstile`, где сервер проверяет подписанные Telegram `initData`, принадлежность атлета родителю и клубу.
Для owner и staff доступен отдельный маршрут `/webapp/staff-pass` и `POST /webapp/staff-open-turnstile`: он не использует student-session, не списывает занятия и пишет событие в аудит.
В панели `admin_turnstile_main` и в общей `admin_keyboard` есть one-tap ссылка на тот же staff-pass, чтобы открыть турникет за один тап.

Админская WebApp-панель `/admin` также сначала проверяет Telegram `initData` и доступна только владельцу клуба или суперадминистратору. API-ключ для открытия админки не требуется.

QR-код имеет формат:

```text
student:<student_id>:<time_salt>:<signature>
```

Подпись проверяется через HMAC. Поддельный или повреждённый QR не передаётся в сервис прохода.

Проход дополнительно проверяет:

- существование атлета;
- принадлежность атлета текущему клубу;
- срок действия абонемента;
- наличие занятий или безлимит;
- повторный проход в активной сессии;
- защиту от быстрых повторных запросов.

`Student.last_visit` используется как маркер активной сессии. После завершения сессии фоновая задача закрывает её и списывает одно занятие. Таблица `visit_logs` хранит отдельную историю всех успешных проходов.

## WebApp-кабинет клиента

Клиентский WebApp-кабинет работает параллельно с Telegram-профилем и не заменяет его.

Рядом с ботом в Telegram есть отдельная кнопка меню `Профиль`:

- она открывает WebApp-кабинет клиента напрямую;
- URL кнопки собирается автоматически с нужным `club_id`;
- для каждого клуба кнопка настраивается отдельно на его боте;
- меню-кнопка больше не перезаписывается сервером автоматически;
- если пользователь открывает бот своего клуба, кнопка ведёт сразу в профиль именно этого клуба.

Меню-кнопка настраивается вручную через BotFather. Сервер не вызывает `setChatMenuButton` при старте и не возвращает кнопку после её отключения владельцем бота.

Сейчас в кабинете есть:

- сводка по атлетам;
- карточка каждого атлета;
- история посещений по атлету;
- история оплат и подписок;
- FaceID/QR-переход;
- бесплатная заморозка;
- покупка заморозки;
- покупка абонемента;
- привязка профиля по номеру;
- кнопка обновления и возврата в Telegram-профиль.

Маршруты WebApp:

- `/webapp/client-cabinet`
- `/webapp/client-cabinet/student`
- `/webapp/client-cabinet/history`
- `/webapp/client-cabinet/freeze`
- `/webapp/client-cabinet/buy-freeze`
- `/webapp/client-cabinet/buy-subscription`
- `/webapp/client-cabinet/auth`

Интерфейс оформлен в едином чёрно-белом премиальном стиле и использует общую mono-тему в `static/css/mono.css`.

## Оплаты

Разовые платежи создаются через ЮKassa. После события `payment.succeeded` webhook:

1. находит заказ по `metadata.order_id`;
2. помечает заказ как `CONFIRMED`;
3. при первой оплате сохраняет идентификатор карты для повторных списаний;
4. начисляет выбранный тариф атлету;
5. отправляет уведомление родителю.

Оплата сохранённой картой выполняется в один клик. Параметры тарифа сохраняются в `PaymentOrder`.

В WebApp покупка абонемента использует тот же платёжный контур: создаётся `PaymentOrder`, затем генерируется `payment_url` ЮKassa. Логика подтверждения платежа и webhook остаются общими для бота и WebApp.

### Платная заморозка абонемента

В профиле клиента доступна отдельная кнопка `❄️ Купить заморозку`, если администратор клуба указал цену одного дня.

Сценарий покупки:

1. клиент выбирает атлета с действующим и ещё не замороженным абонементом;
2. вводит необходимое количество дней — от 1 до 365;
3. система рассчитывает сумму по формуле `количество дней × цена одного дня`;
4. после успешной оплаты сразу продлевает `Student.expire_date` на выбранное число дней;
5. атлет сразу переводится в состояние заморозки (`is_frozen = 1`), а оплаченные дни начинают действовать немедленно;
6. при первом проходе через СКУД заморозка снимается, но добавленные дни остаются в дате окончания абонемента.

Немедленный перевод в заморозку является намеренным поведением: клиент покупает услугу, чтобы начать заморозку сейчас. Если нужно только купить запас дней без немедленного запуска, это должен быть отдельный сценарий — например, баланс или сертификат заморозки.

Платная заморозка не расходует бесплатное право `Student.can_freeze`, но не может быть применена к просроченному или уже замороженному абонементу. Повторная обработка одного платежа защищена статусом `PaymentOrder` и блокировкой заказа.

Бесплатная и платная заморозка тестируются отдельно:

- бесплатная заморозка уменьшает `Student.can_freeze`, ставит `is_frozen = 1`, сохраняет `frozen_at` и `frozen_days`;
- платная заморозка не тратит `Student.can_freeze`, но тоже переводит студента в состояние заморозки и запоминает фактическое число купленных дней;
- при проходе через СКУД `services/gate_control.py` использует `frozen_days` для платной заморозки, а для старых записей — клубный `freeze_days_step`.

Для этого добавлен отдельный тестовый сценарий: покупка платной заморозки, затем первый проход через СКУД. На входе заморозка снимается, а срок сокращается ровно на купленные дни.

Поддерживаются:

- онлайн-оплата новой картой через ЮKassa;
- оплата сохранённой картой;
- перевод по СБП с подтверждением чека администратором.

Типы заказов платной заморозки имеют префикс `FREEZE` (`FREEZE_FIRST`, `FREEZE_RECURRING`). Они обрабатываются отдельно от покупки абонемента, поэтому заморозка не начисляет занятия и не становится шаблоном для будущего автопродления.

Автопродление через `saas_recurrent_payments_job` умеет восстанавливать количество занятий, срок и дисциплину из последнего подтверждённого заказа. Сам запуск cron-задачи сейчас оставлен отключённым в `main.py` и включается отдельно после проверки боевого сценария ЮKassa.

## Загрузочный экран WebApp и логотип

В Telegram-админке откройте `Настройки` и используйте кнопки:

- `🎨 Загрузочный экран WebApp` — включение и базовые параметры;

Логотип сохраняется локально в `static/uploads/logos/`, а ссылка автоматически записывается в настройки клуба. Вручную задавать внешний URL не требуется.

Для логотипа действует ограничение 5 МБ. При сохранении файл проверяется как изображение, приводится к JPEG и уменьшается максимум до 2000×2000 пикселей.

```json
  }
}
```

`duration_ms` ограничен диапазоном от 300 до 10000 миллисекунд. Название клуба берётся из записи клуба, если в старых настройках осталось значение `Новый фитнес-клуб`.

В интерфейсе безлимитные тарифы отображаются как `♾ Безлимит`; технический маркер `999` используется только внутри базы данных и не показывается пользователю.

## Конфигурация

Секреты и подключения задаются через `.env`. Файл не должен попадать в Git.

Основные переменные:

```env
BOT_TOKEN=...
DATABASE_URL=postgresql+asyncpg://...
DB_PASSWORD=...
ADMIN_IDS=...
SECRET_KEY=...
API_STATS_KEY=...
```

Настройки конкретного клуба — в поле `clubs.club_settings`: направления, тарифы, лимиты, ЮKassa, турникет и камеры.

Ключи ЮKassa задаются администратором конкретного клуба через FSM-админку и хранятся в JSONB-настройках клуба:

```json
{
  "payments": {
    "yookassa_shop_id": "...",
    "yookassa_secret_key": "..."
  }
}
```

При обработке webhook система выбирает ключи по `order.club_id`, поэтому разные SaaS-клубы используют свои магазины ЮKassa.

Webhook ЮKassa не требует ручного API-ключа от пользователя. Сервер получает `payment.id` из уведомления и проверяет платёж через официальный API ЮKassa по ключам конкретного клуба, затем сверяет статус, валюту, сумму и `metadata.order_id` с заказом.

Цена платной заморозки задаётся в Telegram-панели администратора: `Настройки клуба` → `Управление лимитами` → `Цена 1 дня заморозки`.

В конфигурации это поле хранится так:

```json
{
  "limits": {
    "freeze_price_per_day": 150
  }
}
```

Значение `0` отключает кнопку покупки для клиентов. Цена задаётся в рублях и может быть дробной. Общая настройка `features.freeze` также должна быть включена.

## Итоговая проверка и готовность к production

По итогам контрольной проверки проект функционально собран и подготовлен к запуску в production:

- автоматические проверки проходят: `75 passed`;
- CI запускает тесты на каждый push в ветку `master`;
- production-деплой выполняется после успешных тестов и использует защищённое окружение GitHub;
- параллельные production-деплои блокируются через workflow concurrency;
- перед обновлением на сервере создаётся SQL-бэкап базы, а приложение создаёт сжатые `.sql.gz`-бэкапы через `pg_dump` без передачи пароля в командной строке;
- админская WebApp проверяет подписанные Telegram `initData` и доступ владельца клуба или суперадминистратора;
- пользовательские проходы и QR защищены проверками клуба, владельца, срока действия и HMAC-подписью;
- контейнер приложения работает от непривилегированного пользователя;
- Nginx настроен с HSTS, защитой от MIME-sniffing, clickjacking и ограничением разрешённых возможностей браузера;
- секреты исключены из Git и передаются через переменные окружения или секреты GitHub.
- Telegram `initData` проверяется криптографически и отклоняется после истечения срока жизни (по умолчанию 24 часа, с небольшим допуском на часы);
- критичные Redis rate-limit операции работают в fail-closed режиме при недоступности Redis;
- ручной API-маршрут `/open-turnstile` требует `X-API-Key`, пользовательский маршрут использует подписанный `initData`;
- `/ready` возвращает HTTP 503 при недоступности базы;
- после Docker-деплоя workflow ждёт готовности API и запускает post-deploy smoke-check.
- проект реально эксплуатируется в клубе: турникет и камеры установлены, кабели проложены самостоятельно, проведены реальные оплаты и проверены основные production-сценарии.

Таким образом, продукт готов к production по коду и базовой инфраструктуре. Перед включением реального трафика остаётся выполнить эксплуатационную приёмку: проверить production-секреты, DNS/TLS, восстановление из бэкапа, тестовый платёж и webhook ЮKassa, Telegram-уведомления, СКУД и камеры на реальном оборудовании. Автосписания следует включать только после успешной проверки боевого сценария ЮKassa.

### CI/CD

Workflow находится в `.github/workflows/deploy.yml`.

- `git push` в `master` запускает тесты;
- ручной запуск workflow (`Run workflow`) после тестов выполняет production-деплой;
- GitHub Secrets: `HOST`, `USERNAME`, `SSH_KEY`, `TELEGRAM_TO`, `TELEGRAM_TOKEN`;
- production environment рекомендуется защитить обязательным approval;
- сервер перед обновлением сохраняет до 10 последних pre-deploy-бэкапов.

### Автоматические бэкапы

Планировщик приложения создаёт бэкап базы и отправляет его суперадминистраторам Telegram. Для работы нужны `DB_PASSWORD`, доступный в контейнере `pg_dump`, и заполненный `ADMIN_IDS`. Перед обновлением Docker Compose дополнительно создаёт SQL-бэкап на сервере.

Сейчас у бэкапа есть базовая политика хранения:

- имя файла включает дату и время создания;
- локально хранятся только последние 14 архивов;
- старые `backup_*.sql.gz` удаляются автоматически после успешного создания новой копии.

Что важно проверять отдельно:

- что архив реально открывается как gzip;
- что бэкап восстанавливается на отдельной тестовой базе;
- что после восстановления совпадают ключевые таблицы и данные, которые важны для клуба;
- что резервная копия хранится не только на сервере, но и во внешнем месте, если это требуется вашей политикой отказоустойчивости.

Если нужен следующий шаг, логично добавить отдельную команду или скрипт `restore-check` для тестового восстановления без риска для боевой базы.

### Restore-check для тестовой базы

Для безопасной проверки копии есть отдельный скрипт:

```bash
python scripts/restore_check.py backup_YYYY-MM-DD_HH-MM-SS.sql.gz
```

Он работает только если заданы переменные тестовой базы:

- `TEST_DB_HOST`
- `TEST_DB_PORT`
- `TEST_DB_NAME`
- `TEST_DB_USER`
- `TEST_DB_PASSWORD`

Логика скрипта:

1. удаляет тестовую базу, если она уже существует;
2. создаёт её заново;
3. восстанавливает в неё указанный backup;
4. завершается с кодом ошибки, если что-то пошло не так.

Это именно проверка копии, а не часть боевого бэкапа. На продакшен-БД скрипт не нацелен.

Файл карты проекта с кратким итогом по WebApp и бэкапам: `PROJECT_WEBAPP_MAP.md`.

Сценарий `restore-check` также покрыт unit-тестом для CI, чтобы проверять саму обёртку без реального PostgreSQL.

## Ограничения и защита от злоупотреблений

Добавлены мягкие ограничения на повторные действия, чтобы не ломать нормальное использование:

- антидубль на создание checkout для покупки абонемента и заморозки;
- блокировка повторной обработки уже подтверждённого payment order;
- блокировки строк при привязке по номеру и при покупке заморозки;
- Redis rate limit на спам-клики по оплате заморозки в Telegram-боте;
- audit-событие для заблокированных попыток.
- при ошибке Redis критичные операции блокируются, а не пропускаются;
- срок жизни `initData` ограничивает повторное использование старых подписанных данных.
- при отказе реле изменения прохода откатываются, поэтому неудачное открытие не превращается в оплаченный/списанный визит;
- QR-пропуск действует только два часовых окна и после этого требует генерации нового кода.

## Важные замечания

- Не удаляйте `.env` с рабочего сервера без резервной копии настроек.
- Не включайте автосписания, пока не проверены тестовая карта, webhook и повторное начисление тарифа.
- Не меняйте схему базы вручную — используйте Alembic.
- Не удаляйте родителей физически из SQLAdmin: у них могут быть связанные атлеты. Используйте редактирование или деактивацию.
- Для production-мониторинга задайте `SENTRY_DSN` и при необходимости `SENTRY_ENVIRONMENT=production`; `init_data`, cookies, API-ключи и authorization-заголовки перед отправкой фильтруются.
- Перед обновлением приложения рекомендуется сделать backup базы.

## Роли и панели управления

- `SUPER_ADMIN_IDS` — Telegram ID суперадминистраторов платформы. Суперадминистратор может работать со всеми клубами.

## Логотип и загрузочный экран WebApp

В меню администратора выберите `Загрузить логотип WebApp` и отправьте изображение фотографией. Система сама сохранит файл в `static/uploads/logos`, запишет внутренний URL и включит загрузочный экран. Вручную URL нужен только для внешнего HTTPS-логотипа, например с CDN.

1. убедитесь, что загрузка завершилась сообщением об успехе;
2. перезапустите контейнер или откройте WebApp заново;
3. проверьте, что открывается адрес `/static/uploads/logos/<имя-файла>`;
4. в Docker не удаляйте volume `app_uploads`, иначе загруженные файлы будут потеряны.

## Короткий чек-лист перед боевым запуском

1. Проверить `docker compose ps` и логи приложения.
2. Открыть WebApp владельцем клуба и убедиться, что чужой `club_id` не даёт доступ.
3. Проверить загрузочный экран и логотип.
4. Проверить QR, Face ID и турникет на тестовом атлете.
5. Провести тестовый платёж и дождаться webhook ЮKassa.
6. Проверить ручную оплату, заморозку и автосписание отдельно.
7. Создать backup и проверить, что файл можно восстановить.
8. Только после этого включать реальные платежи и автосписания.

При проблеме сначала сохраняйте время события, URL/маршрут и фрагмент логов без токенов и паролей. Секреты из `.env` нельзя отправлять в чат, GitHub Issues или логи.

## Ручная продажа товаров за наличные

Администратор может открыть ручную продажу кнопкой `🛒 Продать товар` в основной админ-панели или через `Админ → Настройки клуба → Продажа товаров за наличные`.

Сценарий: нажать `+` у нужных товаров, проверить корзину, количество, остатки и итоговую сумму, затем нажать `Подтвердить оплату наличными`. Количество можно менять кнопками `+`/`−` или вручную.

После подтверждения сервер повторно проверяет остатки с блокировкой строк, списывает товары и создаёт подтверждённую операцию в `CartOrder` с `CartItem` типа `product`. Операция отображается в `/admin/sales` как категория `product` и наличный способ оплаты.

Отдельный складовой экран не нужен: создание и редактирование товаров в `/webapp/admin-products` уже содержит цену, категорию, активность и остаток. На странице продажи показываются только активные товары с положительным остатком.

## Миграции Alembic через Docker

В проекте может быть несколько веток миграций, поэтому контейнер запускает все актуальные heads:

```yaml
alembic upgrade heads
```

После изменения миграций или `docker-compose.yml` пересоберите API:

```bash
docker compose up -d --build gym-api
```

Если контейнер перезапускается и миграция не успевает выполниться, запустите её отдельно:

```bash
docker compose run --rm --no-deps --entrypoint sh gym-api -c "alembic upgrade heads"
```

Проверка результата:

```bash
docker compose ps
docker compose logs -f --tail=100 gym-api
```

В логах не должно быть `Multiple head revisions` или `restart loop`. Не используйте `alembic upgrade head`, пока в проекте остаются несколько heads.
\nКорзина: `/webapp/shop` — отдельная страница покупок, `/webapp/cart` — отдельная страница корзины. Добавление товара, абонемента или заморозки не переводит пользователя в корзину автоматически; позиции сохраняются в `localStorage`.
Корзина поддерживает `+`, `−`, удаление и очистку. Для товаров `+` ограничен текущим остатком, для абонементов ограничение остатка не применяется. Количество абонементов и заморозок учитывается в checkout и повторно обрабатывается webhook по количеству.

## Единые правила статистики и выручки

- «Атлеты» — все строки `students` текущего клуба, включая безлимитные карты с балансом `999` и карточки без абонемента.
- «Родители с привязкой» — количество уникальных непустых `Student.parent_id` в текущем клубе. Это число может быть меньше числа атлетов, потому что один родитель может иметь несколько атлетов, а часть карточек ещё не привязана.
- «Активный абонемент» — дата окончания ещё не прошла, баланс больше нуля и атлет не находится в заморозке.
- «Заморозки» — отдельная взаимно исключающая категория; она входит в удержание, но не в активные абонементы.
- «Осталось занятий» — сумма конечных балансов; маркер безлимита `999` не складывается как 999 реальных занятий.
- Выручка включает подтверждённые `PaymentOrder` и подтверждённые `CartOrder` текущего клуба. Временные границы суток, недели и месяца считаются по Москве, а в БД сравниваются с UTC-naive датами.
- Посещения считаются из `VisitLog`; разбивка по секциям использует тот же источник и поэтому складывается в общее число визитов.

Одинаковые правила используются в `/revenue`, `/admin`, `/admin/sales`, Excel-экспорте,
кнопке дневного отчёта в боте и вечернем автоматическом отчёте.

## Управление товарами и категориями

В админском WebApp каталога товаров (`/webapp/admin-products`) товар можно создать заранее и отключить флагом «Активен», если, например, сегодня не работает бар или временно нет конкретного напитка. Выключенный товар остаётся в каталоге и истории продаж, но не показывается клиентам и недоступен для покупки или кассовой продажи. ## Единый финансовый контур

В отчёты и раздел «Продажи» должны попадать все подтверждённые операции клуба: онлайн-оплата абонементов и заморозок через YooKassa, оплаты из Telegram и WebApp, наличные абонементы, наличные товары и товары из корзины. Наличная продажа товара определяется по префиксу `CASH:`, а наличный абонемент фиксируется как подтверждённый `PaymentOrder` с типом `CASH`; это не влияет на историю и повторную обработку оплат. В продажах доступны фильтры по способу оплаты (карта/онлайн или наличные), категории (абонемент, заморозка, товар), датам, дням недели и дисциплине.
## Касса

Касса открывается из админ-панели отдельной кнопкой. Она не проводит продажи: все подтверждённые доходы — наличные и онлайн — подтягиваются автоматически из общего журнала продаж, а ручные операции предназначены для расходов, прочих доходов и начального остатка. Онлайн-доход показывается отдельно и не увеличивает физический остаток наличных. Доступны фильтры по датам, наличные доходы, онлайн-доходы, расходы и остаток. Каждая ручная операция сохраняет категорию, комментарий, Telegram ID администратора и пишется в аудит; исправления должны выполняться сторно/корректировкой, а не удалением истории.
## Расписание и дисциплины

В клиентском WebApp расписания доступны два фильтра: дисциплина и день недели. В расписание попадают только активные направления клуба. ## Персонал клуба и роли

Владелец клуба остаётся главным администратором и его текущая логика не меняется. ### График работы клуба

Добавлен отдельный WebApp `/webapp/admin-work-schedule` для управления графиком работы клуба. Данные хранятся в `club.club_settings["work_schedule"]`, редактируются из Telegram WebApp и используются планировщиком без отдельной колонки в БД.

Планировщик отправляет график по московскому времени в 11:00:

- в субботу — сообщение вида «Наш клуб работает в субботу по следующему графику»;
- в воскресенье — сообщение вида «Наш клуб работает в воскресенье по следующему графику»;
- в понедельник — сообщение вида «Наш клуб работает в понедельник по следующему графику».

Во всех трёх сообщениях добавлена подсказка: график занятий можно посмотреть во вкладке `Расписание`.

Рассылка берёт именно `work_schedule` из `club.club_settings` и использует только те дни недели, которые переданы в конкретный режим рассылки:

- `sat` — только суббота;
- `sun` — только воскресенье;
- `mon` — понедельник и рабочий блок Пн–Пт.

Контрактные тесты проверяют:

- регистрацию WebApp-графика;
- корректность ключа `work_schedule` в конфиге;
- наличие трёх scheduler-задач в `main.py`;
- текстовые шаблоны рассылки;
- то, что scheduler не отправляет график при пустом `work_schedule`.

## Permanent product contracts (2026-07-28)

Keep these rules when extending the project:

### Attendance and sessions

- All QR, Face ID, bot manual check-in and staff WebApp check-in paths must use `services/gate_control.py:process_athlete_gate_pass`.
- A new session is opened only when `Student.last_visit` is outside `session_timeout_minutes`.
- A repeated check-in during an active session must not create a second lesson deduction or a second parent notification.
- The result must expose `already_marked`/`is_inside_session` so the operator sees that the student is already inside.
- Bot search has two explicit actions: `без турникета` and `с турникетом`.
- Staff WebApp `/webapp/staff-checkin` has the same two actions. `open_turnstile=False` records the visit and session without calling the relay; `True` uses the relay.
- Owners and super-admins have full access. Coaches need both `qr_checkin` and `manual_checkin` permissions.
- Never add an extra Face ID server check on top of the existing signed Telegram WebApp flow: this previously broke working Face ID behavior.

### Parents

- `Student.parent_id` is legacy and must remain intact for existing data and compatibility.
- Additional parents are stored in `student_parents(student_id, parent_id, is_primary)`.
- Phone binding must add a `StudentParent` relation and must not replace an existing primary `parent_id`.
- Every parent-related lookup for access, cabinet visibility, Face ID and notifications must include both the legacy parent and `student_parents`.
- Use `get_student_parent_ids()` to send one notification per unique parent.

### Finance and notifications

- The financial journal must include confirmed online and manual operations for subscriptions, freezes and products, including cash subscriptions (`PaymentOrder` with `CASH` marker).
- For every successful purchase, notify the customer and the club owner. For manual/requisites payments, notify the customer on approval or rejection.
- When a client freezes a subscription, notify the owner.
- On a new student entry, notify all parents and the owner when the entry was made by a staff member. Do not notify again for a repeated active-session check-in.
- Notification failures must be logged and must never roll back a successfully saved visit, freeze or payment.

### Operator locations

- Main admin keyboard: `📝 Отметить посещение` opens student search; each result has `без турникета` and `с турникетом`.
- Staff WebApp cabinet: `Отметить посещение` opens `/webapp/staff-checkin`, with search by name, surname fragment or phone and the same two actions.
- The general admin keyboard contains the single `💰 Касса и журнал` entry. Do not duplicate it inside club settings.

### Athlete history UI

- The athlete card shows current balance, active session end time, `↓ 1 занятие за новый вход`, and a clear note that a repeated entry does not deduct again.
- The history page may be extended visually, but it must not mutate balances or session state.

### Required verification before future changes

- Run `venv\\Scripts\\python.exe -m pytest -q --disable-warnings`.
- Check QR, Face ID, bot check-in, staff check-in with and without relay, repeated check-in, one-parent and multi-parent phone binding, online/manual product/subscription/freeze notifications, and the cash register.

### Payment-method matrix for the cash register

Every confirmed financial operation must be represented by `PaymentOrder` (subscriptions/freezes) or `CartOrder` plus `CartItem` (products). The register and sales journal classify them as follows:

| Operation | Storage | Journal method |
|---|---|---|
| Cash subscription | confirmed `PaymentOrder`, `CASH...` provider/type | `cash` / Наличные |
| Cash product | confirmed `CartOrder`, `CASH:` provider | `cash` / Наличные |
| Online card | confirmed webhook order with provider payment ID | `card` / Карта / онлайн |
| Online SBP | confirmed `FIRST_SBP`/`FREEZE_SBP` or SBP provider order | `sbp` / СБП |
| Requisites/manual transfer | confirmed `MANUAL:` order after owner approval | `requisites` / По реквизитам |
| Manual cash entry | `CashEntry` | cash movement / Ручная операция |

Categories remain independent of payment method: `subscription`, `freeze`, and `product`. A new payment route must create the corresponding confirmed source order and must be covered by the sales and cash-register contract tests; never write only an audit event and expect it to appear in finance.

### Staff onboarding is not client onboarding

- A newly hired employee is identified by `ClubStaff.telegram_id`; they do not need a client `User` record, phone binding, or a student card to open the staff WebApp cabinet.
- The client cabinet bypass applies only to an active owner/staff identity. Ordinary clients still use the normal Telegram/phone binding flow.
- Never create a fake student or bind a staff phone just to make the cabinet open. Staff are not parents and must not inflate parent/client statistics.
- Hiring displays the Telegram name and username when Telegram allows `get_chat`, and sends the employee a role notification.
- Removing a staff member sends an увольнение notification. Notification delivery failures are logged and do not undo the database role change.
