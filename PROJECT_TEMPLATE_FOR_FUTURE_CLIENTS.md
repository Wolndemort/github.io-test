# Шаблон прод-готового проекта для будущих клиентов

## Обязательный финальный gate перед передачей клиенту

Проект считается готовым только после независимой проверки кода, схемы БД,
контейнеров, TLS, backup/restore, платежей и безопасности. Локальный Desktop
не заменяет серверную проверку DNS, firewall, сертификата и callback URL.

### Порядок сдачи

1. Зафиксировать commit и версию образа.
2. Проверить чистую БД: `alembic upgrade heads`.
3. Проверить текущую production БД командой `alembic current` без ручного SQL.
4. Запустить unit/integration tests и post-deploy smoke-check.
5. Выполнить test payment и повторный webhook; боевую оплату не использовать
   как единственный тест.
6. Создать backup и восстановить его в отдельной БД.
7. Проверить TLS, renew, webhook, логи, restart policy и rollback.
8. Передать клиенту только инструкцию и `.env.example`; секреты передаются
   отдельным защищённым каналом.

## Универсальный Alembic-runbook

Каждая миграция должна быть маленькой, идемпотентной по смыслу и проверенной на
копии production. Опубликованные миграции не переписываются: новый фикс — новая
миграция. Для больших таблиц используется expand/backfill/contract. Для каждой
платежной сущности обязательны unique provider id, amount/status validation и
идемпотентный webhook.

```powershell
docker compose exec -T gym-api alembic current
docker compose exec -T gym-api alembic heads
docker compose exec -T gym-api alembic upgrade heads
python -m pytest -q
python scripts/smoke_check.py
```

Перед production применением: backup → staging restore → migration → smoke →
monitoring. Никогда не удалять volume ради «починки» миграции.

## TLS и сертификаты

Боевой сертификат хранится только на сервере в volume Certbot. В локальном
Desktop используется отдельный self-signed сертификат с теми же SAN, но другим
ключом. Боевой private key нельзя коммитить, копировать в проект или передавать
через чат. После renew проверяются `fullchain.pem`, `privkey.pem`, дата
окончания, `nginx -t`, HTTPS и callback URLs.

## Definition of done для нового клиента

- [ ] tenant isolation проверена на двух клиентах;
- [ ] роли owner/admin/superadmin проверены отрицательными сценариями;
- [ ] Telegram initData и QR signature проверяют timestamp и replay;
- [ ] payment webhook проверяет сумму, статус, order/provider id и повтор;
- [ ] DB backup/restore доказан на отдельной базе;
- [ ] миграции чистой базы и существующей базы проходят;
- [ ] все контейнеры имеют понятные restart/health условия;
- [ ] секреты отсутствуют в Git и логах;
- [ ] rollback описан и проверен;
- [ ] README, карта проекта и журнал изменений обновлены.

Это личный чек-лист того, что должно быть в каждом новом проекте, если нужен не MVP, а нормальный прод с запасом.

## 11. Smoke-check

После деплоя должен быть отдельный smoke-check, который проверяет:

- `/health`;
- `/ready`;
- gate-страницу клиентского WebApp;
- gate-страницу FaceID / QR;
- постоянную страницу QR-сканера для планшета над турникетом;
- доступность reverse proxy / Nginx;
- HTTPS / TLS на публичном домене;
- доступность статики и шаблонов, если они есть;
- базовые webhook endpoints;
- при необходимости — тестовый checkout на стенде.

Smoke-check не заменяет тесты.

Он нужен для проверки живого сервиса после обновления.

В текущем проекте workflow после `docker compose up -d --build` ждёт успешные `/health` и `/ready`, затем запускает `scripts/smoke_check.py` внутри контейнера. Smoke-check должен считаться обязательным post-deploy шагом, а не только unit-тестом wrapper-функции.

### Режим входного планшета

Сканер должен открываться один раз в начале смены и не закрываться после успешного QR. QR отправляется в защищённый backend endpoint через `fetch`, а не через Telegram `sendData`, так как `sendData` закрывает WebApp. Endpoint обязан проверять Telegram `init_data`, роль администратора, `club_id`, срок действия и подпись QR. Обработка прохода должна использовать общую функцию СКУД, чтобы не появлялись расхождения между ботом и планшетом. Нужна кнопка ручного завершения смены и защита от повторной отправки одного QR.

### Расписание и продажи

Публичное расписание клуба должно быть доступно любому посетителю в режиме read-only. Администратор получает отдельный защищённый WebApp для добавления, изменения и удаления занятий; ботское управление сохраняется как резервный сценарий.

Для клубов с кофейней и мерчем рекомендуется единая корзина: абонемент, заморозка, товар и напиток оплачиваются одним заказом. Реализация должна быть отдельным слоем, не меняющим стабильные одиночные оплаты до полной проверки. Обязательны раздельные обработчики позиций, идемпотентность webhook, фиксация клуба и безопасное восстановление заказа после частичной ошибки.

Покрывать в первую очередь:

- платежи;
- привязку;
- заморозку;
- gate-логику;
- webhook;
- безопасность;
- race condition.

## 15. CI/CD

В CI должны быть:

- unit-тесты;
- compile-check / py_compile;
- smoke-обёртки;
- проверка Docker build;
- блокировка деплоя при падении тестов.

В CD желательно:

- деплой только после зелёного CI;
- отдельный post-deploy smoke-check;
- проверка health/ready после деплоя;
- понятный rollback-план;
- уведомление о результате деплоя.

Для критичных действий rate-limit не должен работать fail-open: при недоступности Redis операция должна блокироваться и попадать в лог как инфраструктурная ошибка.

Telegram WebApp `initData` нужно проверять не только по HMAC, но и по `auth_date`. Рекомендуемый срок жизни — 24 часа с небольшим допуском на рассинхронизацию часов.

Для СКУД нельзя фиксировать полноценный визит до подтверждения открытия реле. При отказе оборудования транзакция должна откатывать `last_visit` и запись посещения, сохраняя существующую логику таймаута и списания занятия при успешном проходе. QR с часовым salt должен иметь явный срок действия.

## Обязательный UX-аудит перед передачей

Проверяются не только бизнес-правила, но и мелкие действия пользователя:

- нет ли значений `0`, которые приходится стирать перед вводом;
- не создаёт ли двойное нажатие дублирующий запрос или платёж;
- блокируется ли кнопка во время запроса и возвращается ли после ошибки;
- видны ли кнопки привязки контакта, возврата, корзины и поддержки;
- редактируются ли все поля, которые администратор должен менять;
- понятны ли пустые состояния, ошибки сети, недоступный тариф и истёкшая подписка;
- работают ли WebApp-ссылки внутри Telegram на iOS и Android;
- не падает ли сценарий при нескольких атлетах у одного родителя.

межклубная изоляция, HMAC, API-ключи, миграции и фоновые задачи.

Найденный функциональный дефект: отсутствовал POST backend для бесплатной
заморозки из WebApp. Исправление добавлено вместе с авторизацией Telegram,
проверкой владельца атлета, транзакционной блокировкой и уведомлением владельца.
Также устранён `MultipleResultsFound` на `/start` при нескольких атлетах,
добавлены UX-защиты от двойных действий и исправлена видимость контакта.

Перед передачей клиенту обязательно выполнить ручной smoke-сценарий:
новый клиент → контакт → несколько атлетов → кабинет → покупка → корзина →
заморозка → webhook → уведомление владельца → проход → история → возврат.

## Контроль совпадения цифр в отчётах

Перед передачей проекта сверить один и тот же клуб одновременно в WebApp,
админском боте, таблице продаж, статистике и Excel:

1. число атлетов должно включать безлимитных (`999`) и карточки без абонемента;
2. число родителей должно быть отдельной метрикой уникальных привязанных `parent_id`;
3. активные абонементы должны учитывать дату, баланс и заморозку одинаково;
4. выручка должна включать прямые оплаты и подтверждённые заказы корзины;
5. сутки, неделя и месяц должны использовать одну часовую зону — `Europe/Moscow`;
6. общее число посещений и разбивка по секциям должны строиться из `VisitLog`;
7. экспорт не должен отбрасывать безлимитных клиентов.

## Проверка планировщиков

Обязательно проверить:

- родитель с атлетом без абонемента получает кнопку выбора тарифа;
- родитель с пустой датой рождения получает кнопку немедленного заполнения;
- день рождения отправляется один раз в год;
- отсутствие посещений 10+ дней не теряется из-за пропущенного запуска;
- окончание абонемента в ближайшие 3 дня отправляется один раз на дату окончания;
- перезапуск приложения не дублирует сообщения;
- клубы с истёкшей SaaS-подпиской не получают клиентские рассылки;
- атлет без Telegram-привязки не вызывает ошибку планировщика.
