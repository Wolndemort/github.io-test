# Шаблон прод-готового проекта для будущих клиентов

Это личный чек-лист того, что должно быть в каждом новом проекте, если нужен не MVP, а нормальный прод с запасом.

## 1. Базовый скелет

- `main.py` или отдельный entrypoint;
- `handlers/` — бизнес-сценарии;
- `services/` — внешние сервисы и общие утилиты;
- `database/` — модели, сессии, запросы, миграции;
- `middlewares/` — авторизация, контекст, общие проверки;
- `templates/` и `static/` — если есть UI;
- `tests/` — unit и smoke;
- `scripts/` — служебные проверки;
- `docs/` или `.md` — документация;
- отдельный `README.md` или `README.txt`;
- отдельный `.env.example`.

## 2. Обязательные env-переменные

- `DATABASE_URL`;
- `DB_PASSWORD`;
- `SECRET_KEY`;
- `REDIS_URL`;
- `ADMIN_IDS`;
- `API_STATS_KEY` или внутренний service key;
- `BASE_URL`;
- `COOKIE_SECURE`;
- `PUBLIC_HOST`;
- `BOT_TOKEN` или токен интеграции;
- `YOOKASSA_WEBHOOK_SECRET`, если есть платежи;
- `YOOKASSA_SHOP_ID`, если есть платежи;
- `YOOKASSA_SECRET_KEY`, если есть платежи;
- `TELEGRAM_TOKEN`, если есть отправка уведомлений;
- `TELEGRAM_TO`, если есть внешний получатель уведомлений.

Правило:

- секреты только через `.env`;
- `.env.example` обязателен;
- никаких секретов в коде.

## 3. Docker и инфраструктура

- `Dockerfile`;
- `docker-compose.yml`;
- `nginx.conf`, если проект публичный;
- `certbot` / TLS-автопродление, если есть HTTPS;
- healthcheck для базы;
- healthcheck для приложения;
- `depends_on` или аналогичный порядок старта;
- volume для данных базы;
- volume для логов;
- volume для upload-ов, если они есть;
- отдельный контейнер для API/веб-приложения;
- отдельный контейнер для воркеров, если они есть;
- отдельный контейнер для cron / scheduler, если фоновые задачи нельзя держать в API;
- reverse proxy перед публичным приложением.

## 4. Миграции и база

- Alembic или другой нормальный слой миграций;
- запрет ручной правки схемы в проде;
- явные foreign key;
- `ondelete` там, где это важно;
- `unique` там, где дубли недопустимы;
- `index` на поля поиска и фильтрации;
- отдельные таблицы под:
  - users;
  - tenants / clubs / clients;
  - orders;
  - subscriptions;
  - payments;
  - visits;
  - audit;
  - idempotency keys, если платежи чувствительны к дублям.

Если SaaS:

- фильтрация по `tenant_id` / `club_id` в каждом запросе;
- защита от смешивания данных разных клиентов;
- проверки изоляции на уровне middleware и SQL.

## 5. Логика и структура кода

- разделение по доменам;
- отдельный модуль для платежей;
- отдельный модуль для пользователей;
- отдельный модуль для админки;
- отдельный модуль для уведомлений;
- отдельный модуль для WebApp / frontend;
- Telegram menu button рядом с ботом, которая открывает WebApp-профиль клуба по `club_id`;
- отдельный модуль для webhooks;
- отдельный модуль для фоновых задач / cron;
- отдельный модуль для audit;
- отдельный модуль для monitoring;
- отдельный модуль для rate limit / anti-abuse;
- не держать всё в одном файле на тысячи строк.

## 6. Платежи

- idempotency key;
- защита от дублей;
- webhook verification;
- проверка суммы;
- проверка валюты;
- проверка `payment_id` / `order_id`;
- row-lock перед подтверждением заказа;
- повторная сверка статуса у провайдера;
- статусная модель заказа:
  - `NEW`;
  - `PENDING`;
  - `CONFIRMED`;
  - `REJECTED`;
  - `CANCELLED`;
- отдельная логика first payment / recurring payment;
- отдельная логика возврата / отказа, если это нужно.

Нельзя:

- доверять только webhook без проверки;
- зачислять оплату без сверки суммы;
- применять один и тот же заказ повторно.

## 7. Webhooks

- отдельный handler для webhook;
- проверка подписи / secret;
- проверка факта события;
- проверка статуса у провайдера;
- проверка суммы и валюты;
- защита от повторного события;
- логирование retry / ignored / failed;
- понятный ответ `ok / ignored / retry`.

## 8. Race condition и антизлоупотребление

- `with_for_update()` или другой row-lock на критичных записях;
- антидубль на создание оплаты;
- антидубль на привязку профиля;
- антидубль на покупку заморозки;
- rate limit на частые действия;
- audit на `409` и `429`;
- защита от повторной обработки одного и того же события;
- лимит на частые кнопки / спам-клики;
- лимит на повторный checkout;
- лимит на contact binding;
- лимит на опасные admin-actions.

Особенно важно для:

- оплат;
- заморозок;
- автосписаний;
- привязки телефона;
- webhook-обработки;
- ручных подтверждений.

## 9. Audit-лог

- открытие кабинета;
- создание checkout;
- подтверждение платежа;
- привязка профиля;
- покупка заморозки;
- ошибки доступа;
- блокировки по лимиту;
- админские действия;
- изменения настроек;
- все `409`;
- все `429`;
- все security-blocks.

Правило:

- audit не должен ломать основной поток;
- audit не должен менять бизнес-логику;
- audit должен быть структурированным.

## 10. Мониторинг

- `/health`;
- `/ready`;
- логирование HTTP-запросов;
- логирование ошибок;
- readiness check для базы;
- HTTP 503 для `/ready` при недоступной базе;
- readiness check для Redis;
- readiness check для брокера очередей, если он есть;
- отдельный access log;
- отдельный app log;
- отдельный audit log;
- отдельный error log;
- Sentry или аналог;
- метрики;
- уведомления о падениях;
- distributed request id / tracing, если проект большой.

## 11. Smoke-check

После деплоя должен быть отдельный smoke-check, который проверяет:

- `/health`;
- `/ready`;
- gate-страницу клиентского WebApp;
- gate-страницу FaceID / QR;
- доступность reverse proxy / Nginx;
- HTTPS / TLS на публичном домене;
- доступность статики и шаблонов, если они есть;
- базовые webhook endpoints;
- при необходимости — тестовый checkout на стенде.

Smoke-check не заменяет тесты.

Он нужен для проверки живого сервиса после обновления.

В текущем проекте workflow после `docker compose up -d --build` ждёт успешные `/health` и `/ready`, затем запускает `scripts/smoke_check.py` внутри контейнера. Smoke-check должен считаться обязательным post-deploy шагом, а не только unit-тестом wrapper-функции.

## 12. Unit-тесты

- тесты на критичную бизнес-логику;
- тесты на инцидентные сценарии;
- тесты на ошибки и блокировки;
- тесты на idempotency;
- тесты на rate limit;
- тесты на webhook handler;
- тесты на retry / duplicate event;
- тесты на rollback при ошибке;
- тесты на smoke-check wrapper;
- тесты на edge cases валидации.
- тесты на просроченный и будущий `initData`;
- тесты на fail-closed поведение rate-limit при недоступном Redis;
- тесты на защиту ручных API-маршрутов ключом.

Покрывать в первую очередь:

- платежи;
- привязку;
- заморозку;
- gate-логику;
- webhook;
- безопасность;
- race condition.

## 13. Бэкапы

- регулярный backup базы;
- retention;
- проверка целостности архива;
- restore-check;
- описание политики бэкапов в документации;
- test restore на отдельной базе;
- оффсайт-копия, если проект критичный;
- автоматическое удаление старых архивов;
- понятная ручная процедура восстановления.

## 14. README

README должен отвечать на вопросы:

- что это за проект;
- как запустить локально;
- какие env нужны;
- как собрать Docker;
- как прогнать тесты;
- как прогнать smoke-check;
- как сделать бэкап;
- как восстановить;
- где смотреть логи;
- что делать после деплоя;
- как обновлять TLS / certbot;
- как перезапускать Nginx;
- как запускать фоновые задачи;
- как проверять webhooks;
- как делать rollback.

## 15. CI/CD

В CI должны быть:

- unit-тесты;
- compile-check / py_compile;
- smoke-обёртки;
- проверка Docker build;
- блокировка деплоя при падении тестов.

В CD желательно:

- деплой только после зелёного CI;
- отдельный post-deploy smoke-check;
- проверка health/ready после деплоя;
- понятный rollback-план;
- уведомление о результате деплоя.

Для критичных действий rate-limit не должен работать fail-open: при недоступности Redis операция должна блокироваться и попадать в лог как инфраструктурная ошибка.

Telegram WebApp `initData` нужно проверять не только по HMAC, но и по `auth_date`. Рекомендуемый срок жизни — 24 часа с небольшим допуском на рассинхронизацию часов.

## 16. Документация для будущего клиента

- какие функции рабочие;
- какие ограничения есть;
- что уже покрыто тестами;
- где риски;
- что требует ручной проверки;
- как вести прод;
- как обновлять конфиги;
- как делать аварийный откат.

## 17. Must-have минимум для нового проекта

1. `.env.example`;
2. Docker + healthcheck;
3. миграции;
4. structured logging;
5. audit log;
6. tests;
7. smoke-check;
8. backup + restore-check;
9. idempotency;
10. rate limit / anti-abuse;
11. row-lock на критичных местах;
12. README с запуском и прод-процедурами;
13. Nginx / reverse proxy;
14. Certbot / TLS;
15. webhooks verification;
16. cron / scheduler для фоновых задач;
17. rollback plan;
18. отдельные логи для app / audit / errors.

## 18. Практический порядок работ на новом проекте

1. Скелет и конфиг.
2. База и миграции.
3. Логика домена.
4. Безопасность и изоляция.
5. Платежи.
6. Webhooks.
7. Тесты.
8. Smoke-check.
9. Бэкапы и restore-check.
10. Docker и CI/CD.
11. Документация.
12. Rollback-план.

Если этого нет, проект почти всегда потом приходится переделывать.
